# Product Requirements Document (PRD): Customer Module & Merchant Storefront

## 1. Executive Summary
This initiative introduces comprehensive Business-to-Consumer (B2C) capabilities into the existing platform. Previously, the system strictly supported internal administrative roles and merchants/staff. The scope of this document covers the implementation of a self-serving Customer role, private merchant storefront access via exclusive invitation links, a manual payment/checkout flow, and corresponding back-office inventory and profile configurations for merchants.

## 2. User Roles & Definitions
| Role | Description & Scope |
| :--- | :--- |
| **Admin** | Global system administrator managing platform operations (Existing). |
| **Staff / Merchant** | Independent business entities selling goods. Enhanced with store customisation, inventory toggles, and manual payment verification capabilities (Existing + Upgraded). |
| **Customer** | End-users who self-register, discover merchants via unique tokens, place orders, and track transactional histories (New). |

## 3. Functional Requirements

### 3.1 Customer Registration & Authentication
* **Self-Registration:** Customers must be able to create accounts autonomously without relying on Admin provisioning.
* **Unique Identity Fields:** The system requires either an `Email Address` OR a `Phone Number` during registration. At least one field is strictly mandatory and must be unique globally.
* **Deep-Linked Registration Workflow:**
  * If an unauthenticated/unregistered user clicks a specific merchant invitation link, they must be redirected immediately to the Customer Registration Page.
  * Upon successful registration, the system must trigger an automatic login session, navigate directly to the primary Customer Dashboard, and immediately bind/display the referring merchant’s section.

### 3.2 Customer Dashboard
* **Default Null State:** When a new customer logs in without utilizing an invitation link, the dashboard must be entirely blank, displaying no merchant profiles.
* **Dynamic Storefront Sections:** Clicking an exclusive merchant link appends a dedicated section/card for that specific merchant onto the customer's dashboard permanently.
* **Merchant Identity UI Components:** Every added merchant card must visually present:
  * Merchant Profile Picture & Background Banner Image
  * Merchant Registered Business Address
  * Product Category Tagging
  * Business Entity Name & Direct Contact Channels

### 3.3 Exclusive Merchant Storefront
* **Access Control:** Merchants are completely hidden from public discovery. A customer can only access and view a merchant's catalog after capturing the specific deep link generated by that merchant.
* **E-Commerce Catalogue View:** Once authorized, the interface replicates a conventional B2C e-commerce storefront layout where customers can browse active items, view product details, and execute an *Add to Cart* action.

> ⚠️ **CRITICAL LOGIC AMENDMENT: Inventory Control**
> **Correction of Flawed Logic:** Physical or digital inventory must NOT be permanently deducted immediately upon the customer uploading a payment slip. Doing so exposes the system to stock depletion via fraudulent or invalid uploads. Instead, the system must enforce a **Stock Reservation (Hold)** pattern, which is only committed permanently following manual merchant validation.

### 3.4 Checkout and Manual Payment Processing
* **Manual Payment Instruction:** During checkout, the customer is presented with destination payment methods (e.g., bank transfer details) designated by that specific merchant.
* **Proof of Payment Upload:** The customer must upload a digital file/image confirming manual remittance to proceed.
* **State Transition & Notification:** Following a successful upload:
  * A real-time notification is dispatched to the respective merchant.
  * The order status is set to `Pending`.
  * The transaction data is recorded in the merchant’s Sales Log.
  * The items are placed on a conditional **Stock Hold**.

### 3.5 Order Life-Cycle Management
Merchants hold complete ownership over the lifecycle validation of manual payments:
1. **Payment Verification:** The merchant cross-references the uploaded proof with external financial records.
2. **Approval & Dispatch (Status: `Delivering`):** If valid, the merchant updates the order status. At this exact execution point, the reserved inventory is permanently deducted from the main stock block.
3. **Rejection / Cancellation:** If invalid, the merchant rejects the order. The system automatically releases the **Stock Hold**, restoring units back to the merchant's available inventory.
4. **Completion (Status: `Done`):** Once transit concludes, the merchant marks the order fulfilled.
5. **Customer Transaction Ledger:** Customers must have access to a clean historical overview mapping all historical orders across states (`Pending`, `Delivering`, `Done`).

### 3.6 Upgraded Merchant Configuration Suite
* **Storefront Management:** A configuration panel allowing merchants to adjust corporate assets: profile photos, display background banners, business category selections, addresses, and public contact information.
* **Payment Destination Mapping:** Back-office UI allowing input of custom payment guidelines (e.g., Bank Name, Account Identifiers, Account Holder Details).
* **Inventory Visibility Toggle:** Within the updated *Goods Inventory* panel, merchants can actively select and toggle visibility flags (Show/Hide) for individual items to define what populates the customer-facing storefront.
